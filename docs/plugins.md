# Plugins — external extensions for the controller

A plugin is a **separate process** (Python, C#, or any executable) that the
controller launches and supervises. It connects back over a local WebSocket,
announces what it contributes, and from then on can:

- provide **program steps** the builder shows as blocks (parameters and outputs
  declared in a manifest, form generated by the app);
- provide **expression functions** (`scale.tare()`) and **live properties**
  (`$scale.weight`) usable in conditions, expressions and computed variables;
- **subscribe to events** (program lifecycle, step progress, IO changes, robot
  position, status) and **issue any WebSocket command** the controller serves;
- run as a **background service** with a config form the app renders from a
  schema (an MQTT bridge, a database logger, a PLC gateway).

Plugins are trusted code: they run with the controller's privileges, on the same
machine, with no sandbox. The protocol is language-agnostic; SDKs for Python
(`plugins-sdk/python`) and C# (`plugins-sdk/dotnet`) hide it.

This document is the contract between the controller, the SDKs and the app.
Everything here is additive to the existing WebSocket API (`docs/websocket-api.md`).

---

## 1. On disk

```
<data dir>/
  plugins/
    <id>/
      plugin.json            manifest (required)
      main.py | Plugin.dll | bin/…   the code
      requirements.txt       (python, optional)
      .venv/                 (python, created by the controller when requirements.txt exists)
      plugin.log             rolling log (stdout/stderr + protocol log lines), 2 MB × 3
  pluginConfigs/
    <id>.json                { "enabled": true, "token": "…", "config": { … } }
```

`plugins/<id>` is the unit of install/uninstall. `pluginConfigs/<id>.json` is
written by the controller and survives reinstall/upgrade; it is deleted on
uninstall. The folder name must equal `plugin.json`'s `id` (the loader
reports `idMismatch` otherwise).

Discovery happens at boot and on `ReloadPlugins`. Install writes the folder from
a zip and triggers a reload of that one plugin.

Rules:

| Field | Rule |
|---|---|
| `id` | `^[a-z][a-z0-9_]{1,31}$`. Must not be a reserved expression root: `robot program time aux camera stb relay nano plugin global local list time_ms`, nor an existing expression function name. Case-insensitive uniqueness across installed plugins. |
| `protocolVersion` | Must be `1`. Anything else → state `error`, message `unsupportedProtocol`. |
| `runtime` | `python` (`<python> entry args…`), `dotnet` (`dotnet entry args…`), `exe` (`entry args…`, path relative to the plugin folder, executable bit set on Linux by the installer), `external` (nothing is launched; the plugin connects on its own with the token — development mode). |
| `entry` | Required unless `runtime` is `external`. Relative to the plugin folder; must stay inside it. |
| `python.minVersion` | Checked against `python --version` once at start; failure → state `error`, message `pythonTooOld`. |
| `python.requirements` | When the file exists and `.venv` does not, the controller runs `python -m venv .venv` then `.venv/<bin>/pip install -r <file>` before the first start (state `installing`, output in the log). The venv interpreter is then used. Delete `.venv` to force a reinstall. |
| `autoStart` | Default true. Only enabled plugins start; `enabled` lives in `pluginConfigs/<id>.json` (default true on install). |
| `restart.mode` | `always` (default) / `onFailure` (exit code ≠ 0 or lost connection) / `never`. `maxRestarts` (default 5) within 10 minutes, then state `crashed` until a manual start. `backoffMs` default 2000, doubles per consecutive crash, cap 30 s. |
| `readyTimeoutMs` | Default 15000. Launch → `plugin.ready` must arrive in time, else the process is killed and counted as a crash. |
| `configSchema[].type` | `string`, `password`, `number`, `boolean`, `enum`. Optional `help`, `min`, `max`, `step`, `options` (enum only), `required`. Values are stored as given (strings for `string/password/enum`, numbers, booleans). |
| `steps[].id` | `^[a-z][A-Za-z0-9_]{0,31}$`, unique within the plugin. |
| `steps[].params[].type` | `number`, `boolean`, `string`, `enum`, `point`, `list`, `image`, `variable` (see §6). |
| `steps[].outputs[].type` | `number`, `boolean`, `string`, `point`, `list`, `image`. |
| `steps[].timeoutMs` | 0 (default) = none. The step's own `pluginTimeoutMs` overrides. |
| `functions[].name` | `^[a-z][A-Za-z0-9_]{0,31}$`; called as `<id>.<name>(…)`. `timeoutMs` default 250, max 5000. |
| `properties[].name` | `^[a-z][A-Za-z0-9_]{0,31}$`; read as `$<id>.<name>`. `type` is `number` or `boolean` (booleans are 0/1). |

A manifest that fails validation leaves the plugin listed with state `error`
and `message` naming the problem; it is never launched.

## 3. Lifecycle & states

```
disabled → (enable) → stopped → (start) → installing? → starting → running
running → degraded (plugin reported status degraded) → running
running → stopped (StopPlugin, or process exited and restart.mode forbids a restart)
running/starting → crashed (exit, lost socket, ready timeout) → backoff → starting   [until maxRestarts]
error = manifest invalid / runtime missing (never launched)
```

`StopPlugin` sends `shutdown` to the plugin, waits 3 s for the process to exit,
then kills it (`SIGTERM` then `SIGKILL` on Linux, `Kill(entireProcessTree)` on
Windows). Controller shutdown stops every plugin the same way.

Per plugin, the controller keeps: state, `message`, `pid`, `startedUnixMs`,
`restartCount`, `lastExitCode`, `connected` (socket up and ready), `ready`
contributions (the manifest's lists), live property values, and the last 500
log lines (ring buffer) mirrored to `plugin.log`.

## 4. Transport & protocol

### 4.1 Connecting

The controller launches the process with these environment variables:

| Variable | Value |
|---|---|
| `SRC_PLUGIN_ID` | the plugin id |
| `SRC_PLUGIN_URL` | `ws://127.0.0.1:<port>/plugin` |
| `SRC_PLUGIN_TOKEN` | the plugin's token (random 32 bytes, base64url, persisted in `pluginConfigs/<id>.json`; rotated by `RotatePluginToken`) |
| `SRC_PLUGIN_DIR` | absolute plugin folder |
| `SRC_DATA_DIR` | absolute data directory |
| `SRC_CONTROLLER_VERSION` | controller version string |
| `SRC_PARENT_PID` | the controller's own process id. The SDKs poll it every 2 s and exit when it is gone (Python exit code 4, C# `RunAsync` returns), so a force-killed controller never leaves plugins running. On Windows the controller also puts every launched plugin in a kill-on-close Job Object. |

Working directory is the plugin folder. The plugin opens a WebSocket to
`SRC_PLUGIN_URL` and sends `plugin.ready` first (§4.4). The endpoint accepts a
connection only when the first message is a valid `plugin.ready` carrying the
plugin's token; otherwise it closes with code 4401. A second connection for an
already-connected plugin replaces the first (the old socket is closed with 4409).

`runtime: external` plugins get the same token from the app (plugin detail page)
and connect from anywhere that can reach the controller's port.

### 4.2 Framing

JSON text frames, one message per frame, UTF-8. Three shapes:

```jsonc
{ "t": "req", "id": "7",  "method": "controller.command", "params": { … } }   // request
{ "t": "res", "id": "7",  "ok": true,  "result": { … } }                          // reply
{ "t": "res", "id": "7",  "ok": false, "error": "code", "message": "human text" }
{ "t": "evt", "event": "property.set", "data": { … } }                           // notification
```

Both sides may send requests; `id` is a string chosen by the requester and
echoed back. Unknown `method` → `ok:false, error:"unknownMethod"`. A request
that fails validation → `error:"badParams"`. Message size limit 16 MB (images).

### 4.3 Plugin → controller

| Method / event | Params | Result / notes |
|---|---|---|
| **req** `plugin.ready` | `{ token, manifest? , sdk? }` — `manifest` may carry the same `steps/functions/properties` lists to **override** the file's (handy while developing); `sdk` is `{ name, version }` for the log | `{ controllerVersion, pluginId, config, dataDir }`. Must be the first message. |
| **req** `controller.command` | `{ command, params? }` | The command's ACK payload as `result` (whatever the WebSocket API returns; `ok:false` with the ACK's `error` on failure). Any command in `docs/websocket-api.md`. |
| **req** `events.subscribe` | `{ events: ["program.*", "step.completed", …], positionIntervalMs?, statusIntervalMs?, ioIntervalMs? }` | `{ subscribed: [...] }`. Glob `*` allowed as a suffix. Intervals: position min 20 ms default 100; status min 100 default 500; io min 10 default 20. Calling again replaces the subscription. |
| **req** `events.unsubscribe` | `{}` | `{}` |
| **req** `variables.get` | `{ programName? }` | `{ variables: { name: value } , lists: { name: [...] }, strings: { name: "…" } }` — live values when the program is held by an executor (foreground or background); without a name, the global variables. |
| **req** `variables.set` | `{ programName?, values: { name: number|boolean|string|point|array } }` | `{}`. Applied on the executor's loop thread via its pending-action queue (globals directly when no program). Computed variables → `error:"computedVariable"`. Unknown program → `unknownProgram`. |
| **req** `config.get` | `{}` | `{ config }` (schema defaults merged in) |
| **req** `plugin.state` | `{}` | `{ state, enabled, restartCount }` |
| **evt** `properties.set` | `{ values: { "weight": 12.3, "stable": 1 } }` | Replaces those values in the plugin's property table. Names not in the manifest are accepted (shown in symbols as undocumented). Non-numeric values are ignored; booleans → 0/1. |
| **evt** `properties.clear` | `{}` | All properties become unknown (expressions referencing them fail with `unknownVariable`). Also happens automatically when the plugin disconnects. |
| **evt** `log` | `{ level: "debug"|"info"|"warn"|"error", message }` | Appended to the plugin log with a timestamp. |
| **evt** `status` | `{ state: "ok"|"degraded"|"error", message? }` | `degraded`/`error` show on the plugin card; `ok` clears. Does not stop the plugin. |
| **evt** `step.progress` | `{ invocationId, message?, percent? }` | Updates the monitor's current-step description (`<step label>: <message>`). |

### 4.4 Controller → plugin

| Method / event | Params | Expected reply |
|---|---|---|
| **req** `step.execute` | `{ invocationId, stepId, programName, stepName?, params: { key: value }, isBackground }` — values already resolved (§6) | `{ outputs: { key: value } }` on success. `ok:false` with `error` and `message` fails the program with `message`. The plugin may answer long after (no implicit timeout unless the manifest/step sets one). |
| **req** `step.cancel` | `{ invocationId, reason: "stopped"|"reset"|"timeout"|"shutdown" }` | `{}`. Sent when the run ends while the step is outstanding; a late `step.execute` reply is discarded. |
| **req** `function.call` | `{ name, args: [numbers] }` | `{ value: number }` (booleans as 0/1). `ok:false` → the expression throws `pluginFunctionFailed` (program error). No reply within `timeoutMs` → `pluginFunctionTimeout`. |
| **req** `config.changed` | `{ config }` | `{}`. Sent after `SetPluginConfig`. |
| **req** `shutdown` | `{ reason }` | `{}`; then the plugin exits. |
| **evt** `program.started` / `program.resumed` / `program.paused` / `program.stopped` / `program.finished` / `program.error` | `{ programName, isBackground, runCount, error? }` | — |
| **evt** `step.started` / `step.completed` / `step.skipped` | `{ programName, stepId, stepType, stepName?, stepIndex, description }` | — |
| **evt** `io.changed` | `{ changes: { "stb.in1": 1, "nano.Board.pin3": 0 } }` (only changed keys, polled at `ioIntervalMs`) | — |
| **evt** `robot.position` | `{ x,y,z,rx,ry,rz, moving }` at `positionIntervalMs` | — |
| **evt** `robot.homed` / `robot.fault` / `robot.faultCleared` / `robot.estop` | `{ … }` | — |
| **evt** `status` | the `GetStatus` payload at `statusIntervalMs` | — |
| **evt** `plugin.*` | `plugin.started` / `plugin.stopped` `{ pluginId }` for *other* plugins | — |

Event names are dotted; subscription globs: `program.*`, `step.*`, `robot.*`,
`io.changed`, `status`, `plugin.*`, `*`.

## 5. Controller internals (where things live)

```
RobotControl/Plugins/
  PluginManifest.cs        model + validation (→ ManifestProblem list)
  PluginManifestLoader.cs  reads plugins/<id>/plugin.json
  PluginConfigStore.cs     pluginConfigs/<id>.json (enabled, token, config) — AtomicFile
  PluginProcess.cs         launch (python/dotnet/exe), venv bootstrap, stdout/err → log, kill tree
  PluginLog.cs             ring buffer (500) + rolling file
  PluginSession.cs         one connection: framing, request/response correlation, timeouts,
                           inbound dispatch; built on IPluginTransport (WebSocket or in-memory for tests)
  PluginHost.cs            one plugin: manifest + config + process + session + state machine + restart policy
  PluginManager.cs         discovery, install/uninstall, lookup by id, properties table, event bus
                           (PublishEvent), function calls, step dispatch; owns the IO poll thread
  PluginPropertySource.cs  IPropertySource over every running plugin's property table (chain: computed → plugin → robot)
  PluginEvents.cs          event name constants + payload records
RobotControl/Commands/PluginCommands.cs        WebSocket commands (§7)
RobotControl/Hosting/PluginEndpoint.cs         GET /plugin (WebSocket), POST /plugins/install
RobotControl/Execution/Steps/PluginSteps.cs    StepType.Plugin handler
```

Threading: `PluginSession` reads on its own receive loop and dispatches inbound
requests on the thread pool; `controller.command` goes through
`RobotController.AddCommand` exactly like a WebSocket client. Property writes
go into a `ConcurrentDictionary<string,double>` per plugin; reads are lock-free.
`PublishEvent` is non-blocking: each session has a bounded outbound channel
(1024, drop-oldest for `robot.position`/`status`/`io.changed`, never for
program/step events — a full queue for those drops the connection as `slow`).
When the queue is full, any new frame first evicts the oldest queued periodic
event; only a queue holding nothing droppable disconnects (close code 4408,
reason `slow`).

Controller behaviour details (as implemented):

- `state`/`message`: a manifest or launch problem leaves `message` as
  `"<code>: <text>"` (e.g. `unsupportedProtocol: …`, `pythonTooOld: …`). A plugin
  reporting `status` `degraded` **or** `error` shows state `degraded`
  (`statusState` keeps the exact value); `ok` returns it to `running`.
- `external` plugins: `StartPlugin` (or boot, when `autoStart`) puts them in
  `starting` with message `waiting for connection`; a disconnect returns them
  there (no crash/restart). While `stopped`/`disabled`/`crashed`/`error`, a
  `plugin.ready` is refused with 4401. `RotatePluginToken` closes a live
  external connection with 4401.
- A launched plugin's lost socket counts as a crash: the process is killed and
  the restart policy applies. The consecutive-crash backoff resets after the
  plugin stayed ready for 60 s.
- `io.changed`: the first poll after `events.subscribe` sends every IO key (the
  plugin's initial snapshot); later events carry only changed keys.
- Transition events are derived by the same poll: `robot.homed` `{ homed: true }`,
  `robot.fault` `{ joint, message }`, `robot.faultCleared` `{}`.
  `robot.estop` is reserved — the controller has no e-stop signal to report yet.
- The connection must send `plugin.ready` within 10 s of opening.

The step handler never blocks: it sends `step.execute`, records the
`invocationId` in `ctx.PluginState`, returns `Yield`; the reply is enqueued on
`ctx.PendingActions` (checked against `RunGeneration` and the invocation id) and
the handler applies outputs on its next tick. `ResetRunState` cancels any
outstanding invocation with `step.cancel reason:"reset"` — or `"stopped"` when a
user Stop ended the run (a background program's Stop finishes it). A foreground
Stop is a pause: the outstanding step is cancelled (`"stopped"`) and sent again
(a new invocation) when Continue reaches it. Function calls are the one
synchronous path: the loop thread blocks up to `timeoutMs` (default 250 ms);
the docs tell plugin authors to prefer properties for anything live.

Expression integration: the parser accepts dotted call names
(`scale.tare(1)` — `ident(.ident)+` followed by `(`) and builds a call node that
is **resolved at evaluation** through `ExpressionEvaluator.SetDynamicFunctions`
(`Execution/PluginExpressionFunctions` over the live `PluginManager`, installed in
`Program.cs`). Nothing in the parse cache therefore depends on which plugins are
installed, so no invalidation is needed when contributions change
(`ExpressionEvaluator.InvalidateCache()` exists and `SetDynamicFunctions` calls it).
At evaluation an unknown plugin is `unknownFunction`, an unknown function of a
known plugin `unknownPluginFunction`, a wrong argument count `badArity`; a
`PluginFunctionException` (`pluginNotRunning`, `pluginFunctionTimeout`,
`pluginFunctionFailed`) is rethrown as `PluginFunctionCallException`, an
`ExpressionParseException`, so every evaluation path turns it into a program
error with the plugin's message. `ReferencedNames`/`References` report functions
as `pluginId.name` (kind Function, with the argument count). Plugin properties
are resolved by `RobotPropertySource` after its own roots (equivalent to
computed → plugin → robot, since a plugin id can never be a robot root).

Events: `ProgressReporter` (one per executor, foreground and background)
publishes `program.started` (Start), `program.resumed` (Continue),
`program.paused` (PauseProgram step), `program.stopped` (a user Stop — the
foreground pause — or a background program's Stop), `program.finished`,
`program.error` (with `error`), `step.started` (multi-tick steps: moves, waits on
devices/HTTP, Plugin steps), `step.completed` (every executed step; instant
steps report only this) and `step.skipped` (disabled steps, motion steps in a
background program — instead of `step.completed`). `stepIndex` is the count of
completed top-level steps at that moment; `stepName` is omitted when the step has
no name. Payloads are built only when `PluginManager.HasSubscribers(name)` is true
(a lock-free scan of the patterns live sessions subscribed to).

`variables.get` / `variables.set` (wired in `RobotController`): the foreground
executor when it holds the program (running, paused or finished and not reset),
else a running background executor, else `unknownProgram`; without `programName`,
the global store (numbers only; anything else → `badValue`). `get` returns
scalars (computed variables evaluated; no `time_ms`), lists as JSON values and
strings. `set` validates every value first (`computedVariable`, `badValue` — then
nothing is written): numbers/booleans → `Set`, strings → `SetString`, arrays →
`SetList` (a declared list keeps its element type), a point object → a
one-element points list; writes are queued on the loop thread while the program
runs, applied directly otherwise.

## 6. The `Plugin` step

`StepType.Plugin` (additive). Fields on `ProgramStep`:

| Field | Type | Meaning |
|---|---|---|
| `pluginId` | string | manifest `id` |
| `pluginStepId` | string | `steps[].id` |
| `pluginParams` | `{ key: string }` | one entry per declared param; every value is **text** interpreted by the param's type (below). Absent → the manifest default. |
| `pluginOutputs` | `[{ key, variableName }]` | which outputs to write and where |
| `pluginTimeoutMs` | int? | overrides the manifest step timeout (0 = none) |

Param text → value sent to the plugin:

| Param type | Text is… | Sent as |
|---|---|---|
| `number` | an expression (`5`, `$count * 2`) | number |
| `boolean` | an expression; non-zero = true | boolean |
| `string` | a template, `$var`/`{expr}` interpolated | string |
| `enum` | one of `options` (no interpolation) | string |
| `point` | a saved point name, a grid/stack ref syntax as on moves, or `$pts[$i]` — resolved like a move target (local frame **not** applied) | `{ x,y,z,rx,ry,rz }` |
| `list` | a list variable name (with or without `$`) | JSON array (numbers, points as objects, records as objects) |
| `image` | an image variable name | base64 JPEG string |
| `variable` | a variable name; the raw name is passed (for plugins that read/write variables themselves) | string |

Output value → variable write:

| Output type | Plugin returns | Written with |
|---|---|---|
| `number` | number | `Set` |
| `boolean` | bool or number | `Set` (0/1) |
| `string` | string | `SetString` (the variable must be a string variable) |
| `point` | `{x,y,z,rx,ry,rz}` or `[6 numbers]` | `SetList` — the target must be a **points list** variable; it is replaced by a one-element list (read as `$var[0].x`) |
| `list` | array | `SetList` (numbers → number list; objects with x/y/z… → points; other objects → records) |
| `image` | base64 JPEG | `SetImage` |

A missing output key is skipped silently. A type mismatch (string into a number
variable) fails the program with `pluginOutputType`. The step's monitor
description is `"<plugin name>: <step label>"` plus any `step.progress` text.

As implemented:

- `point` param text forms: a saved point name (`P1`); `grid:<grid name>[<row>, <col>]`
  or `grid:<grid name>[<index>]` (needs the grid's `colCount`); `stack:<stack name>[<index>]`
  (names, not ids — an id is accepted as a fallback; each index is an expression);
  `$pts[$i]` (a points variable element); anything else is a template naming a saved point.
- An absent or blank param uses the manifest `default` (sent as written in the
  manifest); no default and `required` → program error
  `<plugin name>: <step label>: parameter '<label>' has no value and no default`;
  no default and not required → the key is not sent. `list`/`image`/`variable`
  names are accepted with or without `$`. An enum text outside `options`, an
  unknown list/image variable or an unresolvable point also error the program.
- Outputs: `number`/`boolean` accept a JSON number or boolean and go to a scalar
  (created when undeclared); `string` needs a declared text variable; `image` an
  image variable (created when undeclared); `list` a list (a declared list keeps
  its element type; a new one is Number/Boolean/Point/Record from the data; an
  array mixing numbers and objects is a mismatch). A mismatch error reads
  `<plugin name>: <step label>: output '<label>' → '$var': <what> (pluginOutputType)`.
- `ok:false` reply → program error `<plugin name>: <step label>: <message>`; a
  plugin that disconnects while the step is outstanding → `pluginDisconnected`.
- `step.progress` → `"<plugin name>: <step label>: <message>"`, with ` (<percent>%)`
  appended when a percent is given (just the percent when there is no message).

A timeout (`pluginTimeoutMs`/manifest) fails the program with
`Plugin step '<label>' timed out after N ms` and sends `step.cancel reason:"timeout"`.
A plugin that is not running when the step executes fails the program with
`Plugin '<id>' is not running`.

### Validation (`ValidateBuiltProgram`) — new codes

| Code | Severity | When |
|---|---|---|
| `unknownPlugin` | error | `pluginId` is not installed |
| `unknownPluginStep` | error | the plugin has no such step |
| `pluginNotRunning` | warning | plugin installed but disabled/stopped/crashed (also for a function or property reference) |
| `pluginParamMissing` | error | a `required` param has no text and no default |
| `pluginParamEnum` | error | enum text not in `options` |
| `pluginOutputType` | error | the mapped variable's kind does not fit the output type (known at validation time) |
| `unknownPluginFunction` | error | `x.y(...)` where `x` is a plugin but `y` is not one of its functions |

Expression validation already reports `unknownFunction`/`badArity`; plugin
functions are checked against the manifest's `minArgs`/`maxArgs`.
`GetExpressionSymbols` gains `plugins: [{ id, name, running, functions: [...], properties: [...] }]`
and also lists plugin functions in `functions` (name `scale.tare`) and properties
in `properties` (name `scale.weight`, with `pluginId`), so the existing expression
assist shows them without changes. In `plugins[]`, `functions` entries are
`{ name, fullName, signature, description, minArgs, maxArgs, timeoutMs }` and
`properties` entries `{ name, fullName, description, type, value }` (bare manifest
names; `value` null until known). In the flat lists, functions carry
`{ name, signature, description, pluginId }` and properties
`{ name, description, type, pluginId, value }`.

Validation details: the plugin checks run only when the controller has a plugin
manager (`ValidationContext.PluginLookup`); a plugin whose manifest is invalid
counts as not installed. `$id.prop` of an installed plugin that neither declares
nor has set `prop` is `unknownProperty`; `x.y()` where `x` is not a plugin is
`unknownFunction`. `pluginOutputType` is also a **warning** for a mapping to an
output key the step does not declare. `grid:`/`stack:` point params naming a
missing grid/stack report `unknownGrid`/`unknownStack`.

## 7. WebSocket commands (additive)

| Command | Params | Response |
|---|---|---|
| `GetPlugins` | — | `{ plugins: [PluginSummary] }` |
| `GetPlugin` | `{ id }` | `{ plugin: PluginDetail }` |
| `GetPluginContributions` | — | `{ steps: [{ pluginId, pluginName, running, step: <manifest step> }], functions: [{ pluginId, pluginName, running, function: <manifest function> }], properties: [{ pluginId, pluginName, running, property: <manifest property>, value?: number }] }` — what the builder needs, in one call |
| `SetPluginEnabled` | `{ id, enabled }` | `{ plugin }`. Disabling stops it. |
| `StartPlugin` / `StopPlugin` / `RestartPlugin` | `{ id }` | `{ plugin }` (returns immediately; state follows) |
| `SetPluginConfig` | `{ id, config: {…} }` | `{ plugin }`. Validated against `configSchema`; on failure the ACK is `ok:false, error:"badConfig", message, field:"<key>"` (`field` is a top-level ACK property); persisted; `config.changed` sent to a running plugin. |
| `GetPluginLogs` | `{ id, start?, end? }` | `{ totalCount, start, logs: [string] }` (same shape as `GetProgramLogs`) |
| `ClearPluginLogs` | `{ id }` | `{}` |
| `UninstallPlugin` | `{ id }` | `{}`. Stops it, deletes `plugins/<id>` and `pluginConfigs/<id>.json`. |
| `ReloadPlugins` | — | `{ plugins }`. Rescans the folder: new folders appear, removed ones vanish (stopped first), changed manifests of stopped plugins reload. |
| `RotatePluginToken` | `{ id }` | `{ plugin }` (external plugins must reconnect) |

`PluginSummary`: `{ id, name, version, description, author, runtime, state, message, enabled, connected, pid, startedUnixMs, restartCount, stepCount, functionCount, propertyCount, hasConfig, statusState, statusMessage }`.
`PluginDetail` = summary + `{ manifest, config, token (external runtime only), properties: { name: value }, logTail: [last 50 lines] }`.

States (`state`): `disabled | stopped | installing | starting | running | degraded | crashed | error`.

`GetStatus` gains `plugins: [{ id, name, state, statusState }]` (additive;
small). The app's status poll can therefore show a badge without extra calls.

HTTP: `POST /plugins/install` — body is the zip (`application/zip`), query
`?replace=true` allows overwriting an existing id. The zip must contain
`plugin.json` at its root or inside a single top-level folder. Responds
`200 { "id": "...", "plugin": PluginSummary }`, `400 { "error": "badZip"|"badManifest"|"idExists", "message" }`.
Max 200 MB (`413 { "error": "tooLarge", "message" }` above it). `GET /plugins/{id}/download` returns the folder as a zip (excluding `.venv`, `plugin.log`).

## 8. SDKs

### 8.1 Python — `plugins-sdk/python/simplerobot_plugin`

Requires Python ≥ 3.9 and the `websockets` package (declared in the SDK's
`pyproject.toml`; a plugin's `requirements.txt` typically contains
`simplerobot-plugin @ file:///…` or a path install). asyncio based.

```python
from simplerobot_plugin import Plugin, StepError

plugin = Plugin()                      # reads SRC_PLUGIN_* from the environment

@plugin.on_ready
async def ready(ctx):                  # ctx.config, ctx.controller_version, ctx.log(...)
    ctx.log("scale ready", level="info")

@plugin.step("weigh")
async def weigh(ctx, params):          # params already typed per the manifest
    ctx.progress("settling…", percent=10)
    grams = await read_scale(params["samples"])
    if grams is None:
        raise StepError("scale timeout", code="scaleTimeout")
    return {"grams": grams, "stable": True}

@plugin.function("tare")
async def tare(ctx, *args):            # must be fast (< timeoutMs)
    return 1.0

@plugin.on("program.started")
async def started(ctx, event):
    await ctx.command("SetSTBOutput", pin=1, value=True)

@plugin.background
async def poll(ctx):                   # runs while connected; cancelled on shutdown
    while True:
        ctx.set_properties(weight=await read(), stable=1)
        await asyncio.sleep(0.05)

@plugin.on_config_changed
async def cfg(ctx, config): ...

plugin.run()                           # connects, handles reconnects with backoff, exits on shutdown
```

`ctx.command(name, **params)` → ack dict or raises `CommandError(code, message)`.
`ctx.get_variables(program=None)`, `ctx.set_variables(values, program=None)`,
`ctx.subscribe(*events, position_interval_ms=…)` (the SDK subscribes
automatically to every event name used in `@plugin.on`). `ctx.set_status("degraded", "no scale")`.
A step handler may `await ctx.cancelled()` / check `ctx.is_cancelled` to react to `step.cancel`.

Also ships `python -m simplerobot_plugin new <id>` which scaffolds a plugin
folder (manifest + `main.py` + `requirements.txt`).

### 8.2 C# — `plugins-sdk/dotnet/SimpleRobot.PluginSdk`

`net8.0` class library (works for `dotnet` and self-contained `exe` runtimes).

```csharp
using SimpleRobot.PluginSdk;

var plugin = new PluginHost();             // reads SRC_PLUGIN_* from the environment

plugin.OnReady(ctx => { ctx.Log("ready"); return Task.CompletedTask; });

plugin.Step("weigh", async (ctx, p) =>
{
    ctx.Progress("settling…", 10);
    double grams = await ReadScale(p.GetInt("samples"));
    return new StepResult { ["grams"] = grams, ["stable"] = true };
});

plugin.Function("tare", (ctx, args) => Task.FromResult(1.0));
plugin.On("program.started", async (ctx, e) => await ctx.CommandAsync("SetSTBOutput", new { pin = 1, value = true }));
plugin.Background(async (ctx, ct) => { while (!ct.IsCancellationRequested) { ctx.SetProperties(new { weight = Read() }); await Task.Delay(50, ct); } });

await plugin.RunAsync();                   // connect, serve, reconnect, exit on shutdown
```

Attribute style is also supported: `[PluginStep("weigh")]`, `[PluginFunction("tare")]`,
`[PluginEvent("program.started")]` on methods of a class passed to `plugin.Register(instance)`.
`SimpleRobot.PluginSdk.Templates` holds a `dotnet new`-style example project
(`examples/dotnet/DemoScale`) that publishes self-contained
(`dotnet publish -c Release -r linux-x64|win-x64 --self-contained`) and a
`plugin.json` with `runtime: "exe"`.

## 10. Reference checklist for implementers

- Wire format stays additive: new step type, new fields, new commands, new
  `GetStatus.plugins`, new `GetExpressionSymbols.plugins`. Nothing renamed.
- Data files may change freely (none of the existing ones do here).
- Linux: paths via `Path.Combine`, venv binary at `.venv/bin/python` vs
  `.venv/Scripts/python.exe`, `chmod +x` for `exe` runtime entries on install,
  process-tree kill via `Process.Kill(true)`, `nohup`-free launch (the plugin is
  a child; the controller's systemd unit reaps it).
- Passwords (`configSchema` type `password`) are never written to logs; the
  `GetPlugin` response returns them as-is (the app masks them, as it does for
  camera passwords).
- Every log line from a plugin is prefixed `[Plugin:<id>]` in the controller
  console as well, at most 20 lines/s per plugin (excess is counted and
  summarised).
